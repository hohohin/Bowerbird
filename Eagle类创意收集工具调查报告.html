★ 执行摘要

如果只读一段，请读这里。Eagle 类工具的「秘密」并不在某个单一技术，而是一组围绕「本地优先 + 性能 + 可扩展」的工程取舍。

它本质是一个本地优先 (Local-First) 的桌面素材数据库，外接一个浏览器「采集探针」与一个本地「AI 加速器」，并用进程隔离的插件系统保证可扩展而不崩溃。
  • 形态：Electron 跨平台桌面应用 + 浏览器扩展，数据 100% 落地用户本地磁盘。
  • 存储：早期版本采用 Electron + JSON，后演进为 SQLite（标签 / 元数据 / 索引）+ 独立缩略图目录 + 原图不修改原则，磁盘 I/O 降至读原图的 1/50–1/10。
  • 采集：浏览器扩展抓取图片 URL，经本地 ws://localhost:{port} 推送给桌面端下载，绕开扩展 5MB 存储限制与下载不稳问题。
  • 检索：全文搜索用 SQLite FTS5；颜色筛选用 K-Means / 中位切分 / 八叉树 主色提取；以图搜图用 pHash 感知哈希 + 汉明距离。
  • AI：语义搜索 / 自动标签 / 图像放大全部 ONNX Runtime 边缘推理，零云端依赖、保护隐私。
  • 插件：独立进程运行，通过 IPC 通信，插件崩溃不拖垮主程序，且不直接访问数据库。

01 什么是「Eagle 类」创意收集工具

先界定品类边界——我们要研究的是一类怎样的工具。

Eagle（eagle.cool）是一款面向设计师的素材 / 灵感收集与管理工具，覆盖「案例、灵感、截图、图片、视频、音频、情绪板」等各类创意素材。它围绕设计师的四大核心工作流设计：收集 → 整理 → 搜索 → 浏览。所谓「Eagle 类工具」，即指具备下列特征的桌面 / 跨端应用：

📥

一键采集

浏览器扩展、拖拽、剪贴板、文件夹监听等多通道，从网页/本地快速收割素材。

🗂️

结构化整理

文件夹、标签、智能文件夹、评分、颜色标注等组织维度。

🔎

多维检索

关键词全文搜索、颜色筛选、形状筛选、以图搜图、AI 语义搜索。

🖼️

极速浏览

海量缩略图瀑布流，支持 PSD/AI/SVG/视频/3D 等格式原生预览。

市场代表产品一览

本报告主角。付费、本地优先、格式支持最全、AI 边缘部署。

🐟 Billfish

关键分野

这类工具最大的技术路线分歧是 本地派（Eagle / Billfish / Pixcall） vs 云端派（mymind / Raindrop / Milanote）。Eagle 选择本地优先，是它能在数万素材下保持极速、并能在无网环境使用的根本原因。

为什么是 Electron？

跨平台（Win/macOS/Linux 一套代码）、可复用庞大 Web 生态、渲染层用 HTML/CSS/JS 快速构建精美瀑布流 UI、主进程用 Node.js 直接操作文件系统与原生模块。代价是体积与内存占用——对「常驻 + 海量图片」的素材工具而言是可接受 trade-off。

为什么是 Local-First？

设计师素材动辄数万、单个 PSD 上百 MB；全量上云成本高、同步慢、隐私敏感。本地存储换来数据主权 + 极速响应 + 离线可用，这正是云端派（mymind / Milanote）被用户诟病「无网即废」的短板。

03 素材采集机制

「收集」是这类工具的第一性体验。Eagle 的采集核心是浏览器扩展 + 本地 WebSocket 隧道。

采集数据流

① 浏览器扩展扫描页面 DOM，提取高清图 URL
→
② 本地 WebSocketws://localhost:{port} 推送
→
③ 桌面端下载器断点续传、UA 伪装、去重
→
④ 入库流水线存图 → 缩略图 → 提色 → 索引
为什么用 WebSocket 而不是扩展直接下载？

① 绕开 Chrome 扩展 localStorage 仅 5MB 的存储上限；② 桌面端下载模块比浏览器扩展更稳定，支持断点续传与大文件；③ 实时性好，比「扩展下载→存指定文件夹→本地应用轮询」的间接方案可靠得多。

扩展抓取图片的典型手段

DOM 扫描

遍历 <img>、背景图 background-image、<picture> / srcset、<video> poster，提取最高清版本。新版扩展还支持批量保存与抓取「受限图片」（懒加载/防盗链场景）。

悬浮保存按钮

向页面注入 content script，在每张图上浮一个「保存到 Eagle」按钮，点击即采集——这是同类工具（Pinterest 保存按钮、mymind）的通用交互范式。

本地多通道采集

🖱️

拖拽

从 Finder/资源管理器或网页直接拖入应用窗口。

📋

剪贴板

复制图片后快捷键粘贴（含截图工具的剪贴板）。

📁

文件夹监听

指定目录自动入库，常配合「截图保存目录」。

⌨️

悬浮窗截图

04 本地存储方案

存储是性能与稳定性的根基。Eagle 的资源库是一个结构清晰的本地目录。

资源库目录结构

# 一个 Eagle 资源库 (Library) = 一个自包含的目录
my-library/
├─ library.db      # SQLite 数据库：标签、元数据、缩略图索引、FTS5
├─ thumbnails/     # 缩略图缓存，统一 JPEG 格式，供浏览模式快速读取
├─ images/         # 原始素材文件，保持原始格式不修改
│   └─ <random-id>.psd
└─ .eaglepack      # 导出包格式（本质是带元数据的 ZIP 归档，可迁移/分享）

三个核心设计取舍

🗄️

SQLite 而非 JSON/NoSQL

素材查询天然是关系型的（多条件筛选 = 多字段 WHERE）。SQLite 单文件部署、跨平台兼容、事务可靠，胜过早期 JSON 方案与 LevelDB 等。

🖼️

原图与缩略图分离

缩略图统一转 JPEG。浏览模式只访问缩略图目录，磁盘 I/O 降至直接读原图的 1/50 – 1/10，对机械硬盘尤其关键。

🔒

原图不修改原则

素材存入后不做格式转换或压缩。好处是数据完整性（不会因转换失败损坏源文件），代价是存储空间不优化。

演进教训：JSON → SQLite

有技术评测指出，Eagle 早期采用 Electron + JSON 存储。但 JSON 本质是「数据交换语言」而非「数据存储与处理」格式——在海量素材下，全量读写、并发、查询性能都吃力。这正是后来迁移到 SQLite 的工程原因，也是 Billfish 等竞品在数据层必须「魔改数据库」才能支撑快速索引的痛点。

关键表结构（推断）

05 缩略图与多格式预览

「秒开数万张图」是这类工具的核心体感，背后是缩略图策略 + 格式解码器。

多尺寸缩略图 + 懒加载

为每张图预生成小/中尺寸 JPEG 缩略图；UI 层虚拟滚动 + 视口懒加载，只解码可见区域，内存占用恒定。

统一 JPEG 缓存

无论原图是 PSD/AI/SVG/RAW，缩略图都转成通用 JPEG。浏览器渲染进程无需为每种格式加载专门解码器，渲染极快。

多格式原生预览的工程难点

PSD / AI / SVG / EPS / 3D / 视频

这些设计格式浏览器原生不支持。实现思路：① 用原生模块（如 libpsd、ImageMagick、各格式 SDK）在主进程 Worker 线程池里栅格化生成预览；② SVG/字体类用矢量直接渲染；③ 视频抽帧做封面 + 内嵌播放器；④ RAW 相片用 LibRaw 解码。这条「格式适配层」是同类工具的核心壁垒之一——格式支持广度直接决定产品力。

对比：Win11 自带照片为何卡顿

系统照片应用用 UWP 即时解码、无预生成缩略图缓存、后台索引耗资源，导致大图秒开困难。Eagle 这类工具反其道行之：预生成 + 缓存 + 分离存储，用空间换时间。

06 颜色提取与筛选

「按颜色找图」是设计师刚需。底层是主色调提取算法，结果入库后用于颜色筛选。

🎯

K-Means 聚类

在 RGB/LAB 空间聚类（K=5~8），质心即主色调。简单高效、无需训练数据，最常用。

✂️

中位切分法 (Median Cut)

递归地把颜色空间按最长轴中位数切分，直到得到 K 个色彩盒。速度快、实现简洁。

🌳

八叉树 (Octree)

用八叉树颜色量化，内存友好，适合实时提取，是经典图像处理方案。

提取流程示意

# Python 伪代码：K-Means 主色提取
from sklearn.cluster import KMeans
import cv2

img = cv2.imread('thumb.jpg')[:, :, ::-1]          # BGR → RGB
pixels = img.reshape(-1, 3)                        # 展平成像素列表
pixels = pixels[::50]                              # 降采样加速

kmeans = KMeans(n_clusters=6, n_init=3).fit(pixels)
palette = kmeans.cluster_centers_.astype(int)          # 6 个主色 RGB
dominance = np.bincount(kmeans.labels_)                 # 各色占比
# → 存入 assets.colors（JSON），供颜色筛选环使用

入库后的颜色筛选 UI

用户点击调色环上的某个色块，系统用「目标色与图片主色的 LAB 距离 ≤ 阈值」做筛选——这是为什么提取时建议在 LAB 空间聚类（LAB 的欧氏距离更贴近人眼色差感知）。

07 全文搜索与以图搜图

检索能力决定「素材库」能否真正被用起来。Eagle 类工具通常提供三种正交检索。

① 全文搜索 — SQLite FTS5

对文件名、标签、注释、OCR 文本建立 FTS5 虚拟表（倒排索引），用 MATCH 做毫秒级模糊匹配。中文需配合分词（simple / trigram tokenizer 或外部分词）。

CREATE VIRTUAL TABLE assets_fts USING fts5(
  name, tags, annotation,
  content='assets', content_rowid='rowid'
);

-- 毫秒级检索：文件名/标签/注释任意命中
SELECT a.* FROM assets_fts f
JOIN assets a ON a.rowid = f.rowid
WHERE assets_fts MATCH '蓝色 海报';

② 以图搜图 — pHash 感知哈希

原理

对图片缩放成 8×8 灰度图 → DCT 变换 → 取低频 → 与均值比较生成 64-bit 哈希。两张图越像，哈希的汉明距离 (Hamming Distance) 越小。

工程加速

把 64-bit hash 拆成多个 BIGINT 列，用 SQL 位运算预筛，避免全表线性扫描；或用 sqlite-vec / sqlite-vss 向量扩展存 CNN embedding 做语义级相似检索。

# 感知哈希 + 汉明距离（以图搜图核心）
def phash(img_path):
    img = cv2.imread(img_path, cv2.IMREAD_GRAYSCALE)
    img = cv2.resize(img, (32, 32))            # 缩放
    dct = cv2.dct(np.float32(img))            # DCT 变换
    dct_low = dct[:8, :8]                  # 取左上低频
    avg = dct_low.mean()
    bits = (dct_low > avg).flatten()
    return ''.join(['1' if b else '0' for b in bits])

# 距离越小越相似（<=5 通常视为近似重复）

③ 形状 / 类型 / 评分筛选

这是结构化字段过滤（宽高比判断横竖方、扩展名判断类型、rating 判断评分），走普通 SQL 索引即可，与上述两种正交组合。

小结：三种检索的关系

全文管「文字能描述的」、pHash 管「长得像的」、语义搜索（见 ⑧）管「感觉接近但说不清的」。三者叠加 + 颜色/形状筛选，构成完整检索体验。

08 边缘 AI 能力

Eagle 的 AI 功能（语义搜索、自动标签、图像放大）全部在本地运行，不上传云端——这是 Local-First 路线在 AI 时代的延伸。

🧩

语义搜索

轻量 CLIP 蒸馏 文本-图像 embedding 模型，CPU 推理。常驻内存，查询走余弦相似度，零网络请求。

🏷️

自动标签

图像分类模型（ONNX Runtime 上的 ResNet/ViT 蒸馏），输出 Top-K 分类作为标签建议。无 GPU 也能秒级完成单图。

🔍

图像放大

Real-ESRGAN 等轻量超分模型，ONNX Runtime 本地执行，批量处理用 Worker 线程池并行。

工程结论：ONNX Runtime + 模型蒸馏

这是当前桌面应用性价比最高的 AI 边缘部署方案——无需 GPU 驱动兼容性处理、无网络依赖、模型可打包进安装包或首启下载缓存。在云端 API 成本上升、隐私监管趋严的背景下，它提供了一条「不上云也能 AI」的可行路线，也是 mymind（云端 AI）之外的另一极。

语义搜索的数据流

① 入库时CLIP 对图片生成 512 维向量
→
② 存储向量入库（sqlite-vec / 本地表）
→
③ 查询时对查询文本同样 embedding
→
④ 余弦相似度Top-K 最近邻返回

模型体积控制在数百 MB，首启加载常驻内存；向量库可用 SQLite 3.45+ 原生向量支持、sqlite-vec 或 sqlite-vss 扩展，保持「单文件、无外部服务」的纯粹本地架构。

09 插件系统：进程隔离

Eagle 4.0 引入的插件系统，允许第三方扩展（AI 放大、智能抠图等）。关键设计是进程级隔离 + IPC。

独立进程运行

插件跑在单独的子进程中，通过 IPC 与主进程通信。插件崩溃不会拖垮主程序——对管理数万素材的资源库至关重要。Electron 可用 child_process.fork() 实现。

技术栈自由 + 受限 API

插件可用 HTML/CSS/JS + Node.js 原生 API + 第三方模块（甚至 Python / 本地二进制），但不能直接访问数据库，只能通过主进程暴露的受限 API（类 RESTful）读写文件，保证安全。

通用启示

当你不信任插件的稳定性时，进程级隔离的成本远低于崩溃恢复的成本。这一模式（VS Code 的 Extension Host、Chrome 的多进程）是桌面应用可扩展性的黄金范式。

插件通信模型

// 主进程：暴露受限 API（伪代码）
const { ipcMain } = require('electron');

ipcMain.handle('plugin:getSelectedAssets', async (e, pluginId) => {
  // 仅返回插件被授权访问的资产，不暴露 DB 句柄
  return assetStore.getSelectedFor(pluginId);
});

// 插件子进程：只能调 API，碰不到底层
const assets = await eagle.item.getSelected();
const upscaled = await runOnnx('realesrgan.onnx', assets);
await eagle.item.replace(upscaled);

10 浏览器扩展 ↔ 本地应用：通信机制对比

这是「收集」环节最关键的技术选型。共有三种主流方案，Eagle 选择了 WebSocket。

方案通信方式优势劣势典型场景
Native Messaging Chrome 官方机制，stdin/stdout + JSON，独立进程 官方支持、安全性高、突破沙箱 需注册 Native Host、配置繁琐、扩展主动发起 RPA 选取网页内容
本地 WebSocket Eagle 选用 本地 App 起 WS Server，扩展作 client 连 ws://localhost App 可主动推送、实时、可靠、支持大文件 需占本地端口、需处理连接保活 素材采集、断点续传下载
本地 HTTP Server 扩展 fetch 请求 localhost 最简单、请求-响应模式 不支持双向推送、CORS 处理 简单一次性请求
为什么不选「文件夹轮询」？

一种 naive 方案是「扩展下载图片→存到约定文件夹→本地 App 轮询该目录」。它的问题：① 实时性差（轮询间隔）；② 扩展下载不稳定、受限图抓不到；③ 多一层落盘冗余。WebSocket 隧道让桌面端直接接管下载，绕开所有这些坑——这是 Eagle 采集又快又稳的根因。

11 竞品技术栈横向对比

  • ✓ 数据主权，文件就在磁盘上，可备份/迁移
  • ✓ 离线可用，数万素材毫秒响应
  • ✓ 隐私天然安全（不上传）
  • ✓ AI 可边缘部署，无 API 成本

  • ✗ 无网即废，依赖平台存活
  • ✗ 数据锁定，导出/迁移困难
  • ✗ 长期订阅成本，大文件上云贵
  • ✓ 但胜在：多端同步、零安装、团队协作、AI 算力强

落地顺序（MVP → 完整版）

1

骨架：本地资源库 + 瀑布流

Electron + SQLite，实现拖拽/文件夹导入 → 存原图 → 生成 JPEG 缩略图 → 虚拟滚动瀑布流浏览。先跑通「存 + 看」。

2

整理：文件夹 / 标签 / 智能文件夹

关系型数据建模，标签多对多，智能文件夹 = 保存的筛选条件。

3

检索：FTS5 + 颜色 + pHash

建 FTS5 虚拟表；入库时跑 K-Means 存主色；计算 pHash 存库。三种检索正交组合。

4

采集：浏览器扩展 + 本地 WebSocket

桌面端起 WS Server，扩展抓 DOM 推 URL，桌面端下载入库。这是体验飞跃点。

5

AI：ONNX 边缘部署

集成 CLIP（语义搜索）+ 分类模型（自动标签）。可选 Real-ESRGAN 放大。模型首启下载缓存。

6

生态：进程隔离插件系统

fork 子进程跑第三方插件，IPC + 受限 API。开放扩展能力同时保证主程序稳定。

一句话路线

Electron + SQLite/FTS5 + 本地 WS 采集 + ONNX 边缘 AI + 进程隔离插件——这是一条被 Eagle 验证过、可在数万素材下保持极速的成熟工程路线。

∑ 总结与展望

回到最初的问题：Eagle 类创意收集工具到底是怎么实现的？

它不是一个「黑科技」，而是一组克制而精准的工程取舍的组合：把数据库放本地、把缩略图与原图分离、把下载交给桌面端、把 AI 跑在 CPU 上、把插件关进子进程。
  • 本地优先是这类工具的灵魂——数据主权、极速、离线、隐私，一举四得。
  • SQLite + 缩略图分离 + 原图不修改是性能三角，让数万素材秒级响应。
  • 浏览器扩展 + 本地 WebSocket是采集体验的关键，比文件夹轮询可靠得多。
  • FTS5 / K-Means / pHash / ONNX四件套，覆盖从文字、颜色、图像到语义的全维度检索。
  • 进程隔离插件是可扩展性与稳定性的平衡术。

🔮 趋势：本地 AI 普惠化

随着 ONNX Runtime / Apple Silicon NPU / 端侧小模型成熟，「不上云的 AI」会越来越强。mymind 式的「AI 替你整理」体验，将能在本地复刻且不牺牲隐私——这正是 Eagle 类工具的下一个增长极。

⚖️ 待解的张力

本地派与云端派的根本张力是「数据主权」vs「多端协作」。未来的赢家可能是一个本地优先 + 可选端到端加密云同步的混合体——既保留 Eagle 的所有权与速度，又获得 mymind / Milanote 的多端便利。
